# PM Template Improvement Suggestions

*Gaps or friction points observed in this project's PM structure, including proposed CLAUDE.md changes. Reviewed periodically and promoted to the template repo (`X.-Claude-Project-Framework`) when accepted.*

-----

## 2026-08-07 - Dashboard "next steps" heuristic is unreliable, and its doc is out of sync with its code

*Status: `Proposed`*

**Observation:**

CLAUDE.md's "Project Dashboard Compatibility" section says the dashboard "pulls the first 5 unchecked `- [ ]` lines (in file order) as next steps." Investigating this project's dashboard card (which was showing stale/paused items ahead of active Phase 4 work), we found the dashboard's actual code takes the *last* 5 unchecked lines, not the first — CLAUDE.md and the implementation have drifted apart.

But fixing the slice direction alone doesn't solve the underlying problem: raw file-order position is a bad proxy for "current work" once a project has paused or future phases interleaved with active ones. In this project, Phase 3 (PAUSED) sits earlier in the file than Phase 4 (the actual active phase) but contains the most recently-touched work (a FreeRouting autorouter session from 2026-08-05/06), while Phase 4's own heading was stale — labeled `*(Not yet started)*` despite being 4/6 complete. Neither "first N" nor "last N" reliably surfaces true current priorities; the ordering needs to be phase-aware, and phase-status labels need to be trustworthy for that to work.

**Suggested change:**

1. Fix the dashboard's parser to derive "next steps" from phase headings rather than raw line position — e.g., skip phases whose heading is marked `PAUSED`/`Future`, and prefer unchecked items from the most-advanced phase with any checked items (a proxy for "currently active").
2. That fix only works if phase-status labels stay accurate. Add a rule (Session End Routine or Work Package Conventions) that the phase heading must be updated the moment the first item in that phase is checked off, so labels like "Not yet started" don't go stale while work is actually happening (as Phase 4 did here).
3. Once the dashboard's actual logic is corrected, update the "Project Dashboard Compatibility" section in CLAUDE.md to describe the corrected (phase-aware) behavior — not just flip "first" to "last," which would just document the current bug instead of fixing it.

## 2026-08-13 - WP3.1/Phase 3 mislabeling: 5 sessions of active Phase 4 work logged under a heading marked PAUSED

*Status: `Proposed`*

**Observation:**

A fifth adversarial PDR (2026-08-13) flagged that `3. Work Packages.md`'s Phase 3 ("Custom PCB -- Battery Variant") is still headed `*(PAUSED 2026-08-04, see Decisions Log)*`, but its child section WP3.1 ("PCB Design Onboarding") has accumulated the entire placement/routing/adversarial-review history for the *active* barrel-jack board (Phase 4) across five sessions -- everything from initial layout through five PDR rounds. Meanwhile Phase 4's own WP4.1 still carried an unchecked `@claude` line item ("PCB layout for the barrel-jack board") that had actually been done long ago, superseded by the WP3.1 work (closed as a stale duplicate this same session). This is the same underlying failure mode as the 2026-08-07 dashboard finding above (phase-status labels going stale while real work happens under a differently-labeled section) but this time it happened entirely within this project's own Work Packages file, not a downstream dashboard consumer -- meaning it wasn't just a display bug, it actively mislead the record of which phase real work belongs to.

**Suggested change:**

1. When placement/routing work for a specific board variant continues across multiple sessions, log it under that variant's own active-phase WP section, not wherever it happened to start (WP3.1 was originally scoped as PCB-tooling-onboarding shared by both variants, but organically became the barrel-jack board's entire layout log).
2. Add a periodic self-check (perhaps at Session End Routine, perhaps a standing PM Improvement audit) that flags when a `*(PAUSED)*` or `*(Future)*` phase has had checkbox activity more recent than the phase directly below it marked `*(In Progress)*` -- that mismatch is a strong, cheap-to-detect signal of exactly this drift.
3. Don't move the existing WP3.1 history now -- it's a large, accurate, useful record; relabeling or migrating it risks losing the trail of decisions. Better to fix forward: keep future barrel-jack work under WP4.1/Phase 4 headings going forward, and treat WP3.1 as a closed historical record once its remaining open items (if any) are resolved.

## 2026-08-07 - Session Start Routine should require a `git pull` before trusting local state

*Status: `Proposed`*

**Observed:** A session found staged/unstaged/untracked changes in the local checkout that were built on a base 2 commits behind `origin/main` (real FreeRouting work, but against a since-reverted J7 connector that had already been removed on `main`). Applying it would have silently undone completed work and erased two Session Log entries. This project has hit local-checkout staleness at least twice before (see Session Log 2026-08-03: "Local main checkout is stale (8 behind origin)").

**Suggested change:** `CLAUDE.md`'s "Session Start Routine" (currently 3 steps: read WP/Session Log/Audits, flag STARTED entries, confirm priorities) should add an explicit step 0: `git fetch` and pull/fast-forward the local checkout before reading any PM files or trusting `git status`, so decisions aren't made against stale state. Pairs with the user's standing preference that Claude owns both `git pull` and `git push` going forward, not just push.
