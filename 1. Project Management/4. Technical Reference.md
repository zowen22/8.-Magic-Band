## Enclosure Notes

- Ornament shell: 3D printed
- Barrel jack: 5.5mm/2.1mm panel-mount, requires **11mm hole** in shell
- Orient jack on bottom — cable exits downward, follows ornament wire naturally
- Minimum 15mm clearance behind jack inside shell for solder tabs + wiring
- Nano footprint: 18mm × 45mm — plan mounting accordingly

## RF Workflow (per unit)

1. Run `Sniffer.ino` with receiver on pin 2 — press all remote buttons, record codes
2. Fill `RF_CODE_ON`, `RF_CODE_OFF`, `RF_BITS`, `RF_PROTOCOL` in Rev4
3. Flash Rev4, put outlet in learn mode, scan any RFID card to pair
4. Confirm outlet responds, ship pre-paired

## Known Constraints / Gotchas

- Nano VIN accepts 7–12V regulated but 5V works fine from a regulated supply
- MFRC522 is 3.3V — use Nano's 3V3 pin, not 5V
- DFPlayer audio file must be named `001.mp3` on the SD card root
- rc-switch `send()` is blocking — NeoPixel animations must complete before RF fires
- 433MHz is fire-and-forget (no ACK) — send code 5× to ensure reception (`RF_REPEAT`)
- Nano has Mini-USB for programming; power in production via VIN barrel jack

If this WSL2 instance ever gets nuked, or you're setting up on a new machine, this is
the complete path from nothing to "flashing sketches from a WSL terminal." Assumes
Windows + WSL2/Ubuntu already installed — that part isn't covered here.

### 3. USB passthrough (Windows ⇄ WSL2)

The board connects via USB to Windows and is **not** visible in WSL by default — needs
a bridge every time it's (re)connected.

**One-time, Windows (Admin PowerShell):**
```powershell
winget install usbipd
```

**One-time, WSL (regular interactive terminal — needs real sudo):**
```bash
sudo apt-get update
sudo apt-get install -y linux-tools-generic hwdata
sudo update-alternatives --install /usr/local/bin/usbip usbip /usr/lib/linux-tools/*-generic/usbip 20
sudo usermod -aG dialout $USER
```
After `usermod`, open a **new** terminal window — group membership doesn't apply
retroactively to the shell you ran it from (`newgrp dialout` also works if `newgrp`
happens to be installed; wasn't on this machine's minimal Ubuntu image, so a fresh
terminal was the actual fix used).

**Every time the board is (re)connected, or after a reboot — Windows (Admin PowerShell):**
```powershell
usbipd list                    # find the board's BUSID
usbipd bind --busid <BUSID>    # one-time per device, not per session
usbipd attach --wsl --busid <BUSID>
```
Our board enumerates as CH340, VID:PID `1a86:7523`. Keep that PowerShell window open —
the attach only holds while it's running (or use `usbipd attach -a` for auto-reattach).

**Then, WSL:**
```bash
arduino-cli board list   # should show /dev/ttyUSB0 once attached
```

**Arduino over WSL — full recurring gotcha list (confirmed 2026-08-14, one long bench session
flashing/testing RF_TX_Test and RF_TXRX_Loopback):**

1. **Every reconnect needs a fresh `usbipd attach`, and reconnects happen a lot** —
   not just physical unplug/replug or a Windows reboot, but also: connecting/disconnecting
   a module wired to the board (confirmed — hooking up the RF TX module mid-session caused
   a real kernel-level `USB disconnect` per `dmesg`, not just a serial hiccup, almost
   certainly a brief power brownout from the extra current draw/momentary contact), and
   killing/restarting `arduino-cli monitor`. Symptom is always the same: `arduino-cli board
   list` (or `ls /dev/ttyUSB0`) comes back empty. Fix is always the same: re-run
   `usbipd attach --wsl --busid <BUSID>` from an admin PowerShell.
2. **The device node's permissions reset on every reconnect** — new enumeration means a
   fresh `/dev/ttyUSB0` owned `root:dialout` at `crw-rw----`, unreadable/unwritable by a
   non-dialout user regardless of any earlier `chmod`. Group membership (`usermod -aG
   dialout`) only takes effect in a *new* shell session, which doesn't help mid-session —
   the fast fix that works immediately is `sudo chmod 666 /dev/ttyUSB0`, run interactively
   by the user (an agent can't supply the sudo password itself; ask the user to run it and
   confirm via `ls -la /dev/ttyUSB0` showing `crw-rw-rw-` rather than guessing).
3. **From a Claude Code background job specifically**, the default sandbox hides
   `/dev/ttyUSB0` even once it's attached and `chmod`'d — pass `dangerouslyDisableSandbox:
   true` on any Bash call that touches the device (`board list`, `compile`+`upload`, reading/
   writing the port directly). See the corrected "Dead ends" entry above — this is a
   per-command override, not a hard wall.
4. **`arduino-cli monitor` and `arduino-cli upload` can't share the port** — a monitor left
   running (yours or a leftover background one) makes upload fail with `Device or resource
   busy`. Check with `ps aux | grep ttyUSB` and kill the PID before flashing; the monitor
   needs restarting afterward if you still want the live view.
5. **Opening the serial port resets the board** (DTR toggle, standard Arduino
   auto-reset-into-bootloader behavior) — writing immediately after `open()` loses the
   byte, since the sketch hasn't finished (re)booting yet. For a scripted write+read in one
   shot, open a single persistent file descriptor, sleep ~2.2s for boot to finish, then
   write and read on that same fd — two separate `open()` calls (one to write, one to read)
   each reset the board independently and can lose data between them:
   ```bash
   bash -c 'exec 3<>/dev/ttyUSB0; sleep 2.2; printf o >&3; timeout 3 cat <&3'
   ```
6. **A live `Monitor`/background `tail` on `/dev/ttyUSB0` directly hits the same sandbox
   `/dev` restriction as #3**, and `Monitor` has no `dangerouslyDisableSandbox` escape hatch.
   Workaround: run `cat /dev/ttyUSB0 > logfile` as a `dangerouslyDisableSandbox: true`
   background Bash task, then point `Monitor`/`tail -f` at the regular log file instead of
   the device node directly.

### 5. KiCad (PCB design)

No root/apt available in this sandbox — installed via the official AppImage, extracted
manually (no FUSE), not run in place.

```bash
mkdir -p ~/.local/opt && cd ~/.local/opt
# grab the current AppImage from https://www.kicad.org/download/linux/ — 10.0.5 is what's installed here
chmod +x kicad-10.0.5-x86_64.AppImage
./kicad-10.0.5-x86_64.AppImage --appimage-extract        # produces ./squashfs-root

mkdir -p ~/.local/bin
ln -s ~/.local/opt/squashfs-root/usr/bin/kicad-cli ~/.local/bin/kicad-cli
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc  # skip if already added in step 2
```
Launch the GUI — appears via WSLg automatically, no X server setup needed, **but force
software rendering** (see gotcha below, confirmed 2026-08-05):
```bash
LIBGL_ALWAYS_SOFTWARE=1 ~/.local/opt/squashfs-root/usr/bin/kicad
```
**First launch does one-time global library setup** — this is a real GUI-only step
(tracked as WP3.1, can't be done headlessly). KiCad will prompt to configure the global
symbol and footprint library tables; accept the defaults. Despite this being the "lite"
AppImage variant, both `usr/share/kicad/symbols` and `usr/share/kicad/footprints` **are**
bundled locally under `~/.local/opt/squashfs-root/` (verified 2026-08-05 — earlier notes
in this project claiming "no bundled footprint library" were wrong; no network fetch is
needed for standard parts).

`pymupdf` (Python) is already available in this environment, no separate install needed —
used to render datasheet PDFs to images locally for pin-diagram verification when
`poppler-utils`/`pdftoppm` isn't available (root-blocked, same constraint as everything
else here).

### 6. FreeRouting (autorouter)

Runs headless once you have a Specctra DSN file — but two steps around it are GUI-only in
KiCad 10.0.5 (no `kicad-cli` equivalent exists for either):
1. **DSN export**: `pcbnew` → File → Export → Specctra DSN
2. **Session re-import**: `pcbnew` → File → Import → Specctra Session (then **Fill Zones**
   again — the copper pour doesn't auto-recompute against newly-imported tracks/vias, and
   DRC will show a wave of bogus `0.0000mm` clearance violations until you refill)

**Setup (one-time):**
```bash
mkdir -p ~/.local/opt
# freerouting.jar (v2.2.4): https://github.com/freerouting/freerouting/releases
# needs a JRE with class file version >= 69 (Java 25) -- confirmed the error otherwise:
#   UnsupportedClassVersionError: ... compiled by a more recent version ...
# a JDK 17 JRE will NOT work. Grab a JDK 25 JRE (e.g. Eclipse Temurin) and extract to
# ~/.local/opt/jre25/
```
Both files must live under `~/.local/opt/` (or somewhere else persistent) — **not** `/tmp`,
which is ephemeral in this environment and won't survive a reboot/reset.

**Run:**
```bash
~/.local/opt/jre25/jdk-25.0.4+7-jre/bin/java -jar ~/.local/opt/freerouting-2.2.4.jar \
  -de "<board>.dsn" \
  -do "<board>.ses" \
  -mp 50 \
  --gui.enabled=false
```
`-de` = design (input DSN), `-do` = design output (session file), `-mp` = max passes.
Config/logs land in `/tmp/freerouting/` (`freerouting.json`, `freerouting.log`) — that's
FreeRouting's own default (`java.io.tmpdir`), fine to leave ephemeral, only the jar+JRE
need to persist. On the 40x40mm 2-layer board here: 42 unrouted nets → 0, 4 passes, ~2.5s.

**Gotcha (confirmed 2026-08-10):** despite running via CLI args, FreeRouting can still pop
up a GUI dialog (data-collection/review consent) when a display is reachable (WSLg here) —
this silently blocks the process between "routing complete" and actually writing the `.ses`
file, no CLI error, just a multi-minute hang until someone dismisses the popup by hand.

First attempted fix — editing `/tmp/freerouting/freerouting.json` to set
`gui.enabled`/`allow_telemetry`/`allow_contact` to `false` — **didn't hold**: the popup
itself writes its own values back to that file (GUI source, priority 50 in FreeRouting's
own settings-precedence ladder — see `docs/settings.md` in the freerouting repo), so it
silently reverted between runs. **The reliable fix is the `--gui.enabled=false` CLI flag**
shown above (priority 60, always beats the file and any GUI write-back). Always pass it
explicitly on every invocation rather than relying on the JSON file's persisted state.

### 7. Placement & Routing Workflow (end-to-end)

The full cycle used repeatedly on 2026-08-09/10, split by who does which half:

1. **User, in `pcbnew`:** move/place components as needed.
2. **User:** if the move was substantial (moved something that already had routing near
   it), select-all tracks/vias with the Selection Filter set to Tracks+Vias only, delete,
   then **Fill Zones (B)**. For a small/isolated move this step can often be skipped —
   FreeRouting will just re-route whatever's now broken and leave the rest alone.
3. **User:** File → Export → Specctra DSN, overwrite `<board>.dsn` in the same folder.
4. **User:** tell Claude "exported" (or similar).
5. **Claude:** run FreeRouting (see section 6 above for the exact command, always with
   `--gui.enabled=false`). Report the unrouted-net count before/after.
6. **User:** File → Import → Specctra Session, then **Fill Zones (B)** again (the pour
   doesn't auto-recompute against newly-imported copper), then save.
7. **Claude:** run `kicad-cli pcb drc`, regenerate `board_top.svg`/`board_bottom.svg`,
   commit + push to `main`, update Work Packages/Session Log.

**When FreeRouting can't finish some nets** (stalls at N unrouted, "board state has not
changed... cannot make further progress"): don't fight it with more passes, just finish
those specific nets by hand in `pcbnew` — usually faster and it's exactly what interactive
routing is for:
- Press **X** on a pad/net to start an interactive route, click to lay down segments.
- Press **V** *while still actively dragging* to drop a via and hop to the other copper
  layer at that point — the standard way around an obstacle on the current layer.
- To change an **existing** trace: select it and press **G** (drag, keeps connections
  intact — not **M**, which is a bare move and leaves the trace behind) then **V** mid-drag
  to hop layers, or for a trace whose both ends already land on a via/THT pad, just
  right-click → **Properties** and change the **Layer** field directly, no via needed.
- After a manual fix, re-export DSN and run FreeRouting again if you want it to pick up
  and finish anything else — it treats already-routed nets as done and only works on what's
  left (confirmed 2026-08-10: a re-run after a manual fix reported "started with 0 unrouted
  nets" and exited immediately).

**If a Specctra session import ever comes back corrupted/fails**, don't fight it: revert
the uncommitted `.kicad_pcb` (`git restore` back to the last commit, or File → Revert in
`pcbnew`) rather than trying to debug a broken `.ses` — cheaper to redo the move and
re-export than to chase corruption. Delete the stale `.dsn`/`.ses` too so there's no
confusion about which export is current.

### Dead ends — don't retry these

- **Launching KiCad under WSLg with default (hardware) OpenGL rendering** — symptom:
  window opens but appears frozen/unresponsive, and hovering over it makes the mouse
  cursor disappear entirely; clicks don't register. This is a WSLg GPU-passthrough
  rendering glitch (KiCad's canvas uses OpenGL, passed through to the Windows host GPU
  driver via WSLg's virtual GPU layer), not an app hang — confirmed by killing and
  relaunching with `LIBGL_ALWAYS_SOFTWARE=1`, which fixed it immediately (2026-08-05).
  **Always launch KiCad with that env var set** (see launch command above) until this is
  root-caused properly — likely candidates if it needs a permanent fix: `wsl --update`
  from an admin Windows PowerShell, or a Windows-side GPU driver update. Software
  rendering is slower but fine for a 40x40mm board.
- **Using "Update PCB from Schematic" (F8) on `MagicBand_BarrelJack`** — confirmed broken:
  the board's PCB footprints are missing the `path` attribute that links them back to their
  schematic symbol's UUID (likely from earlier direct `.kicad_pcb`/`.kicad_sch` S-expression
  edits that bypassed the normal netlist-import flow — see the placement-fix and J7-removal
  entries in `5. Session Log.md`). Without that link, F8 can't recognize any existing PCB
  footprint as already-placed, so it treats every schematic symbol as new and adds a
  duplicate footprint for each one, right on top of the originals (confirmed 2026-08-10,
  reverted without saving). For any future footprint swap on this board, use PCB-side
  **Change Footprint(s)...** directly (select the footprint, right-click) instead — it
  doesn't depend on the broken schematic linkage. F8 also first requires the schematic be
  annotated (Tools → Annotate Schematic, "keep existing annotations") even though every
  symbol already has a normal numbered reference — that's a separate, harmless prerequisite
  check, not related to the duplication bug.
- **Expecting a `pcbnew` Python module in this AppImage install** — confirmed absent (not
  assumed). Headless PCB scripting is limited to `kicad-cli`'s DRC/ERC/export subcommands
  plus direct `.kicad_pcb`/`.kicad_sch` S-expression text editing — no programmatic
  board-object API here.
- **Expecting `kicad-cli` to export Specctra DSN for autorouting** — not present in KiCad
  10.0.5; that export is GUI-only (`File → Export → Specctra DSN`). FreeRouting itself
  runs fine headless (portable JRE, no root needed), but there's no way to hand it a board
  without the GUI export step first. See "FreeRouting (autorouter)" above for the working
  headless recipe once you have a DSN in hand.
- **Running FreeRouting with whatever `java` happens to be on PATH** — this jar needs a
  JDK 25+ JRE specifically; anything older (confirmed: JDK 17) fails immediately with
  `UnsupportedClassVersionError`. See "FreeRouting (autorouter)" above.
- **Mapping `\\wsl$\...` as a network drive** (`net use`, `New-PSDrive -Persist`,
  Explorer's "Map Network Drive" wizard) — all fail with "network name no longer
  available," or loop on a credential prompt that goes nowhere. The share works fine for
  *browsing* in Explorer or passing a raw UNC path as a CLI argument — just not for
  persistent drive mapping.
- **Opening sketches in Arduino IDE via a `\\wsl$\...` path** — the IDE's file-open
  dialog silently creates a blank `sketch_xxxx` instead of loading the real file, even
  when the dialog itself accepted the path. Legacy Windows file APIs mishandling UNC
  paths, not a content problem. Drag-and-drop from an open Explorer window onto the IDE
  window works around it; better to just skip the IDE GUI entirely (step 4 above).
- **~~Doing any of this from a Claude Code background job~~ — corrected 2026-08-14, this
  was wrong.** A background job's default sandbox has a restricted `/dev` view that hides
  `/dev/ttyUSB0` even after a successful `usbipd attach` (symptom: `ls`/`cat`/`arduino-cli
  board list` all report "No such file or directory" despite `dmesg` showing the kernel
  genuinely bound the device). But this **is** just a per-command sandbox restriction, not
  a hard mount-namespace wall — passing `dangerouslyDisableSandbox: true` on the specific
  Bash call gives it real access, and a background job can compile, flash, and read/write
  serial over USB passthrough exactly like an interactive terminal once that's set. See
  "Arduino over WSL — full recurring gotcha list" below for the complete flow.
